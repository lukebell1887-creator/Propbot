## Executive Summary

After reading every line of the test script, the live engine, the Rust math kernel, the HMM regime detector, the AKAD risk calculator, the risk supervisor, the MT5 bridge, and the MQL5 EA, I found **5 concrete discrepancies** between what the backtest tested and what the live bot actually runs. **The backtest results ($62K portfolio profit, 75% WR) were generated by code that does NOT match the live engine in several important ways. You cannot trust the backtest numbers until these are aligned.**

## CRITICAL DISCREPANCY #1: Amplitude Gate Expected Profit Formula

**Severity: CRITICAL — Directly changes which trades are taken**

### What the TEST does (test_oil_index_live.py, line ~185):
```python
expected_profit = abs(z) * sigma * lots * pdef.notional
```
Uses the **FULL absolute Z-score** as the expected move.

### What the LIVE engine does (engine.py, line ~510):
```python
z_captured = max(0.0, abs(state.last_z) - state.last_exit_z)
expected_profit = z_captured * spread_sigma * lots * cfg.notional
```
Uses only **(|Z| - exit_z)** — the Z-distance the spread will actually travel from entry to exit.

### Impact:
For a typical Oil entry at Z=2.2 with exit_z=0.5:
- **Test expected profit**: 2.2 x sigma x lots x notional = **100% of Z**
- **Live expected profit**: (2.2 - 0.5) x sigma x lots x notional = **77% of Z**

For a marginal entry at Z=2.05 with exit_z=0.5:
- **Test**: 2.05 x sigma (full) 
- **Live**: 1.55 x sigma (**24% less**)

**The test OVERESTIMATES expected profit by 23-40% depending on Z-value.** This means:
- Trades that pass the amplitude gate in the test may be BLOCKED in live
- The test takes more trades, including marginal ones that inflate the backtest WR
- The live bot correctly blocks some of these but the backtest never trained/optimized around this stricter filter

### The Bible says (v5.6.4):
> "Corrected formula: (|Z| - exit_z) x sigma = actual capture"

The live engine has the CORRECT formula per the Bible. **The test script was never updated to match.** So your $52K Oil backtest profit includes trades that the live engine would have blocked.

## CRITICAL DISCREPANCY #2: HMM Hold for Oil — 10 (Test) vs 5 (Live)

**Severity: CRITICAL — Changes regime filter behavior for every Oil trade**

### What the TEST uses (test_oil_index_live.py, line ~165):
```python
best_hmm_per_pair = {"Oil Spread": 10, "Index Spread": 20}
```
Oil runs with `min_regime_hold = 10`.

### What the LIVE engine uses (engine.py PairConfig, line ~122):
```python
PairConfig(name="Oil Spread", ..., hmm_min_hold=5, ...)
```
Oil runs with `min_regime_hold = 5`.

### Impact:
`min_regime_hold` controls how many M1 bars the HMM must stay in a regime before it can change. This is a hysteresis mechanism to prevent regime flapping.

- **HMM hold=10**: Regime changes after 10 bars of sustained new regime. More stable, fewer false regime transitions.
- **HMM hold=5**: Regime changes after only 5 bars. More reactive, but also more prone to regime flapping — can flip to "volatile" (BLOCKED) on brief spikes, then flip back.

**With hold=5, the live Oil HMM will:**
1. Block entries more often during brief volatile spikes (trades the backtest would have taken)
2. Unblock faster after volatility subsides (trades the backtest would have still been blocking)
3. Potentially create a different set of entry windows that don't match the backtest at all

The test specifically found HMM=10 was "best from previous 2-year test" but the live engine hardcodes HMM=5. **The live engine does not match the tested optimal configuration.**

## MODERATE DISCREPANCY #3: Amplitude Gate Cost Calculation Bug

**Severity: MODERATE — Commission cost formula is wrong in live engine**

### What the TEST does (test_oil_index_live.py):
```python
spread_cost = (pc.spread_a_per_fill * 2 + pc.spread_b_per_fill * 2) * lots * mult
# Oil: (4*2 + 5*2) * lots * mult = 18 * lots * mult
commission = pc.commission_pct * OIL_NOTIONAL_PER_LOT * lots * 4
# Oil: 0.0003 * 6500 * lots * 4 = 7.8 * lots
total = spread_cost + commission
# Oil: 18 * lots * mult + 7.8 * lots
```
Commission uses multiplier **4** (4 fills: open+close x 2 legs). Commission scales **linearly** with lots.

### What the LIVE engine does (engine.py, line ~520):
```python
base_spread_cost = (cfg.spread_cost_a + cfg.spread_cost_b) * 2.0  # = 18 for Oil
commission_cost = cfg.commission_pct * cfg.commission_notional * lots * 2.0
# Oil: 0.0003 * 6500 * lots * 2 = 3.9 * lots
total_cost = (base_spread_cost * tod_mult + commission_cost) * lots
# Oil: (18 * mult + 3.9 * lots) * lots = 18 * mult * lots + 3.9 * lots^2
```

### Two bugs compounding:

**Bug A: Commission multiplier is 2 instead of 4**
- Test: `commission_pct * notional * lots * 4` (4 fills — correct for round trip of 2-leg spread)
- Live: `commission_pct * notional * lots * 2` (only counts 2 fills — misses the close fills)

**Bug B: Final multiplication by lots makes commission quadratic**
- `commission_cost` already contains `lots`, then the whole expression is multiplied by `lots` again
- This makes commission scale as `lots²` instead of `lots`

### Net effect at typical Oil lot sizes:

| Lots | Test Cost (London) | Live Cost (London) | Live vs Test |
|------|-------------------|-------------------|-------------|
| 0.01 | $0.258 | $0.180 | Live 30% LOWER |
| 0.05 | $1.290 | $0.901 | Live 30% LOWER |
| 0.10 | $2.580 | $1.804 | Live 30% LOWER |
| 0.50 | $12.90 | $9.98 | Live 23% LOWER |
| 1.00 | $25.80 | $21.90 | Live 15% LOWER |

**At typical lot sizes (0.01-0.10), live underestimates costs by ~30%.** This makes the amplitude gate MORE permissive in live, letting through trades that should be blocked.

Combined with Critical #1 (lower expected profit), the effects partially cancel — but NOT perfectly. The amplitude ratio in live is:
```
live_ratio = (LOWER expected) / (LOWER cost) ≠ test_ratio = (HIGHER expected) / (HIGHER cost)
```
The gate makes DIFFERENT decisions about which trades to take vs block, creating a different trade population.

## MODERATE DISCREPANCY #4: Time-of-Day Spread Multipliers

**Severity: MODERATE — Different cost scaling at different hours**

### Test (test_oil_index_live.py):
```python
def get_spread_multiplier(hour):
    if 0 <= hour < 7: return 1.8      # Night/Asian
    elif 7 <= hour < 9: return 1.2    # Pre-London
    elif 9 <= hour < 17: return 1.0   # London/NY overlap
    elif 17 <= hour < 21: return 1.1  # US afternoon
    else: return 1.5                   # Night
```
**5 time zones**, uses CSV bar timestamp (data time).

### Live (engine.py):
```python
if broker_hour < 2 or broker_hour >= 22:
    tod_mult = 2.5   # Night session
elif broker_hour < 8:
    tod_mult = 1.5   # Asian session
else:
    tod_mult = 1.0   # London/NY session
```
**3 time zones**, uses **broker server time** (which may have a GMT offset).

### Key differences:
| Hour | Test Multiplier | Live Multiplier | Delta |
|------|----------------|-----------------|-------|
| 0-2 | 1.8 | 2.5 | Live 39% HIGHER |
| 2-7 | 1.8 | 1.5 | Live 17% LOWER |
| 7-8 | 1.2 | 1.5 | Live 25% HIGHER |
| 8-9 | 1.2 | 1.0 | Live 17% LOWER |
| 9-17 | 1.0 | 1.0 | Match |
| 17-21 | 1.1 | 1.0 | Live 9% LOWER |
| 21-22 | 1.5 | 1.0 | Live 33% LOWER |
| 22-24 | 1.5 | 2.5 | Live 67% HIGHER |

**Additional complication**: The test uses the timestamp from the CSV data (which is the bar's own time). The live uses `broker_hour` from `_get_broker_now()` which applies a GMT offset. If the broker is GMT+2 (common for Fintokei), then what the test sees as "hour 15" the live sees as "hour 17". This shifts the entire multiplier schedule by 2 hours, meaning the live bot's cost estimates during morning/evening sessions don't match the test at all.

## MINOR DISCREPANCY #5: Price Source (Close vs Mid-Price)

**Severity: MINOR — Small systematic difference**

### Test:
```python
pa = float(row['close_a'])  # M1 bar close price from CSV
pb = float(row['close_b'])
```

### Live:
```python
def _get_price(self, symbol):
    tick = self._get_tick_data(symbol)
    return (tick.bid + tick.ask) / 2.0  # Mid-price from live tick
```

The test feeds bar close prices directly. The live feeds mid-prices from the most recent tick at M1 bar close time. For tight-spread instruments (Index), these are nearly identical. For Oil (wider spreads), the mid-price can differ from the close by a few cents, creating slight Z-score drift that accumulates over the Welford window.

**Impact**: Small but systematic. Over 768 bars of pre-warm + ongoing trading, the Welford mean and variance will be slightly different between test and live, meaning Z-scores won't be exactly the same even on identical market conditions.

## ROOT CAUSE ANALYSIS

### Why the live bot is losing while the test shows 75% WR:

**1. The backtest is more optimistic than the live engine (Critical #1)**
The test's amplitude gate uses `abs(z)` for expected profit, overestimating by 23-40%. This means the test takes marginal trades that the live engine correctly blocks. The test's 75% WR includes trades the live bot never takes.

**2. Different HMM regime filtering for Oil (Critical #2)**
The test used HMM hold=10 (more stable regimes), but the live runs HMM hold=5 (faster regime changes). This creates a completely different set of entry/exit windows. Trades the test entered during "stable regime 0" windows may not exist in the live bot's view because HMM hold=5 may have briefly flipped to regime 2 (BLOCKED) during a noise spike.

**3. Cost asymmetry in amplitude gate (Moderate #3)**
The commission bug means the live engine uses different cost estimates than the test. Since the amplitude gate is the final gatekeeper for Oil entries, different cost estimates = different trade selection = different P&L.

**4. Time zone mismatch in cost multiplier (Moderate #4)**
The test and live use completely different time-of-day cost schedules, and the live uses broker time (with GMT offset) while the test uses data time. During Asian/night sessions when Oil entries are marginal, the amplitude gate makes different accept/reject decisions.

### The compound effect:
These aren't independent issues — they COMPOUND. The amplitude gate (which has the wrong formula, wrong costs, and wrong time multipliers) decides which trades get taken. The HMM filter (with different hold values) decides which entry windows exist. Together, the live bot is operating on a fundamentally different trade population than what was backtested.

## RECOMMENDED FIXES

### Fix 1: Align amplitude gate formula in test script (Critical)
Change `test_oil_index_live.py` line ~185:
```python
# BEFORE (wrong — uses full Z):
```

Then RE-RUN the backtest to see the REAL numbers with the corrected formula.

### Fix 2: Align HMM hold for Oil (Critical)
Either change the live engine to HMM=10 (matching the tested optimum):
```python

```
OR re-run the test with HMM=5 to get the real numbers for the live config.

### Fix 3: Fix commission bug in live engine (Moderate)
```python
# engine.py, in _maybe_enter, amplitude gate section:
```

After aligning the test script to match the live engine exactly, re-run `test_oil_index_live.py`. The resulting numbers will be the TRUE expected performance of the live bot. If the numbers are still good (PF > 1.5, WR > 65%), the system is sound. If they collapse, the original backtest was overfit to its own bugs.
